# 企业 AI 平台 1.0 决策闭环演示设计

**日期：** 2026-08-24  
**对象：** 管理层与客户  
**建议时长：** 15 分钟，另预留 5 分钟问答  
**状态：** 待业务方审阅

## 1. 演示目标

以一个管理者能够理解的真实工作链路说明平台价值：企业可以把外部变化和内部知识转化为可追溯的管理建议，由人审批后定向送达，而不是得到一段无法验证、无法落实的聊天回复。

本次演示完成后，观众应能回答三件事：

1. 平台如何缩短“发现变化到形成行动建议”的时间；
2. 为什么建议可验证、可控且不会绕过管理者；
3. 决策如何进入企业协作流程，而非停留在 AI 对话框中。

## 2. 推荐叙事

演示采用“外部变化驱动的管理决策”场景。以招聘和人力资源动态为例，AI 先检索近期可信公开信息，再生成三条管理建议；管理者查看来源与建议，作出审批，最后查看定向交付状态。随后在 AI 分析台说明同一平台可把企业知识带入分析上下文。

这不是功能巡游。每一屏都回答一个业务问题：

| 顺序 | 管理问题 | 平台回答 |
| --- | --- | --- |
| 1 | 今天哪些事项需要我决策？ | 驾驶舱集中呈现待办和待审批事项。 |
| 2 | 外部变化如何转化为行动？ | 智能决策任务以真实网络检索生成结构化建议。 |
| 3 | 我能否信任这份建议？ | 每条来源含标题、URL、发布时间与检索时间；模型正文链接不算证据。 |
| 4 | 谁为最终决定负责？ | 建议先进入 pending，只有管理者批准后才改变决策状态。 |
| 5 | 决策如何真正落地？ | 平台通过幂等 outbox 定向交付，并显示真实的发送状态。 |

## 3. 演示范围与口径

### 3.1 主链路

```text
驾驶舱
  -> 智能决策任务
  -> 真实网络检索与来源校验
  -> 结构化管理建议
  -> 人工审批
  -> 定向通知交付状态
  -> AI 分析台中的企业知识追问（收束）
```

### 3.2 可以对外说明的事实

- 正式入口为 `http://106.53.85.84:8092/`；2026-08-24 检查 `/ready` 返回 200，数据库与 RAG worker 均 ready。
- 正式发布记录已验证一次网络检索、结构化智能决策、审批和飞书 outbox `sent` 的闭环；数据库迁移 head 为 `20260823_0022`。
- 平台使用 React/Vite 前端、Nginx、FastAPI、PostgreSQL 16/pgvector、异步 worker 和私有 Hermes HTTP 边界。浏览器不直接取得 Hermes、嵌入或飞书密钥。
- 知识检索先按服务端派生的组织、成员和资源权限过滤；RAG worker 独占嵌入供应商密钥。
- 决策审批使用版本与幂等键，通知通过 outbox 异步交付；没有配置飞书时系统会报告 `feishu_not_configured`，不把失败显示成成功。

### 3.3 不作为本次卖点的能力

- 不演示用户删除、邀请撤销、Profile 停用、归档/永久删除等破坏性操作。
- 不把 Skills Hub、AI skill generation、Mem0 兼容边界或提醒通知说成已上线的真实外部能力；部分实现仍是 mock 或仅服务层能力。
- 不把钉钉机器人列入本轮主链路；其机器人、白名单与 pairing 仍需独立准备。
- 不承诺“自动决策”。平台输出的是待审批建议，管理者保留最后决定权。

### 固定演示提示词

```text
检索过去 7 天与制造企业招聘、人力资源管理相关的公开动态。
请形成一份给总经理的中文管理建议：
1. 提炼三项最值得关注的变化；
2. 每项给出一条可在两周内启动的行动建议；
3. 使用 Markdown 输出；
4. 只采用能够展示标题、URL、发布时间和检索时间的来源。
```

若现场数据与“制造企业”不匹配，保留任务结构，只替换为已获授权的业务主题，不能使用真实员工个人信息、客户保密资料或未脱敏经营数据。

## 5. 现场准备与兜底

### 5.1 T-30 分钟检查

1. 访问 `/ready`，确认 HTTP 200 和 `database=ready`、`rag_worker=ready`。
2. 使用专门的演示账号从 `/` 登录，确认其具备 pipeline、dashboard、chat 与 knowledge 所需权限。
3. 确认已有一个演示知识目录和不含敏感内容的知识条目；知识库上传前必须先选定目录。
4. 用演示提示词预跑一次任务，确认真实来源与 Markdown 输出；保留其 pending 或 approved 结果作为备用路径。
5. 查看 delivery status。若计划实际发送飞书，逐项确认平台专用凭据、唯一测试目标、路由和接收授权；否则不触发新的外部消息。
6. 关闭无关浏览器标签、消息通知和包含个人或生产敏感数据的页面。

### 5.2 故障处理

| 现场情况 | 主持人口径 | 操作 |
| --- | --- | --- |
| 新任务仍在执行 | “系统正在完成检索和结构化校验；不会为赶演示伪造完成状态。” | 切换到预跑完成的同主题任务。 |
| 搜索供应商不可用或无校验证据 | “没有可验证来源时，平台不会把模型正文当成最新事实。” | 展示预跑任务和来源字段，不重试外部发送。 |
| 飞书未配置/目标未授权 | “通知通道是显式授权能力，未配置时保留失败状态而不是静默发送。” | 展示 `/api/delivery/status` 的业务化解读与正式验收记录。 |
| 前端门户回退或通知提示异常 | “该入口不属于本次核心链路。” | 直接导航到 `/`、`/pipeline`、`/chat` 或 `/knowledge`。 |
| 登录问题 | 不在现场重置真实用户密码。 | 使用预先确认的演示账号或离线录屏备用。 |

## 6. 架构说明页

技术说明只保留一页，服务于“可控、可信、可运营”三个业务承诺：

```text
浏览器（驾驶舱 / AI 分析台）
  -> Nginx（统一入口，SSE 不缓冲）
  -> FastAPI（JWT、组织/权限、审计、API）
  -> PostgreSQL + pgvector（业务、决策、知识、记忆事实源）
     -> pipeline / delivery / RAG / memory workers
     -> 私有 Hermes 边界与供应商工具
     -> 经授权的飞书定向交付
```

话术：平台的中心不是“大模型聊天”，而是企业工作流。前端只调用平台 API；组织范围由服务端从登录身份派生；外部密钥、原始文件路径和内部 runner 不进入浏览器；真正发送使用后台可重试、可观察的 outbox。

## 7. 成功标准

本次演示成功不以“所有按钮都点到”为标准，而以以下五项均被观众理解为标准：

1. AI 能将外部变化组织成业务可用的候选决策；
2. 每个关键事实有来源和时间，不能以生成文本替代证据；
3. 管理者可以审批、退回或要求重生成，AI 不越权；
4. 决策有状态与交付轨迹，可以进入协作动作；
5. 企业资料、权限和外部密钥都处在平台控制边界中。
