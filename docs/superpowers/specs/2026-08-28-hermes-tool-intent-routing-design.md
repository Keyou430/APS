# Hermes 工具意图路由与结构化操作入口设计

## 背景

平台 AI 已通过主 Hermes 暴露飞书和行业新闻 MCP。现有故障中，用户要求总结指定飞书群聊的开发进度，Hermes 却调用了 MCP 协议自带的 `list_resources`。两个 MCP 没有发布静态 Resource，空结果被模型错误解释为“没有业务资料”，实际的 `lark_cli_execute`、飞书用户授权和群聊数据均正常。

问题本质是工具语义和决策边界不清晰，不是服务、权限或数据缺失。修复不能把自然语言意图判断搬到后端，也不能为每句话增加关键词分支。

## 目标

1. 自然语言意图仍由 Hermes 判断。
2. Hermes 能区分 MCP 静态 Resource 与可执行的业务 Tool。
3. 外部实时数据或用户私有业务数据请求优先尝试对应业务 Tool。
4. MCP 静态资源为空不得作为“业务数据不存在”的证据。
5. 飞书群名请求可自主完成“查群、读消息、总结”的完整链路。
6. 定时任务、日程等字段较多或会产生写入的操作提供结构化入口，但保留自然语言入口。
7. 不重复实现已经存在的任务草稿、确认、看板和智能决策能力。

## 非目标

- 不在后端用飞书、新闻等关键词直接替 Hermes 执行业务操作。
- 不将所有对话改成表单或固定命令。
- 不移除通用 `lark_cli_execute`，也不限制 Hermes 只能使用少量飞书能力。
- 不把 MCP Resource 机制用作飞书数据目录。
- 不在本次改造中新增多账号、多租户或新的审批模型。

## 方案选择

采用“自然语言优先、结构化入口兜底”的混合方案。

仅增加提示词的方案改动最小，但模型仍可能把协议工具和业务工具混淆。全部改为按钮和表单虽然稳定，却违背平台 AI 应像 Hermes 一样自然对话的目标。混合方案通过统一工具契约提高自主调用可靠性，同时只在复杂写操作上提供确定性入口。

## 架构

### 1. Hermes 工具选择契约

主 Agent 会话每轮都向 Hermes 传递稳定的工具选择契约。该契约描述决策原则，不解析具体业务关键词：

- 当回答依赖外部实时数据、用户私有系统或已连接服务时，先使用匹配的业务 Tool 获取证据。
- `list_resources` 和 `read_resource` 只处理 MCP Server 显式发布的静态 Resource。
- `list_resources` 返回空列表只表示服务器没有发布静态 Resource，不表示业务 Tool 无数据或不可用。
- 不得在尚未尝试可用业务 Tool 时要求用户复制粘贴资料。
- 工具失败时根据结构化错误选择帮助、Schema、替代业务 Tool 或向用户报告具体权限和参数问题。
- 不得把工具调用失败伪装成“没有资料”。

契约由平台作为 Hermes instructions 提供，但不指定当前问题属于哪个业务域。意图识别和工具选择仍由 Hermes 完成。

### 2. MCP 工具语义

强化主 Hermes 可见的业务工具描述：

- `lark_cli_help` 用于发现飞书业务域和 shortcut 的参数说明。
- `lark_cli_schema` 仅用于 typed OpenAPI，不用于 shortcut，也不读取业务数据。
- `lark_cli_execute` 明确用于真实飞书业务数据，包括按名称查群、读取群消息、读取任务、读取或写入云文档等。
- `industry_news_latest` 明确用于读取固定来源的真实行业新闻。

飞书 MCP Server instructions 增加常见只读链路示例。示例用于告诉 Hermes 如何组合工具，不根据用户文本直接触发执行：

1. 不知道群 ID 时，先查询 `im +chat-search` 帮助并按群名搜索。
2. 得到 `chat_id` 后执行 `im +chat-messages-list`。
3. 根据用户要求处理时间区间、分页和总结。

### 3. 结构化操作入口

在现有 AI 对话框复用任务草稿确认交互，增加两个紧凑快捷入口：

- 创建定时任务
- 添加日程

点击后只填充可编辑的结构化消息模板，不直接创建数据。模板字段包括：

定时任务：任务目标、执行频率、时区、数据来源、输出要求、是否立即执行。

日程：标题、日期、开始时间、结束时间、时区、参与人、地点或会议方式、备注。

结构化模板包含明确的业务类型标记。平台将该标记作为 intent hint 传给 Hermes，作用仅限缩小工具域和要求字段校验，不替 Hermes生成最终参数，也不绕过用户确认。

定时任务继续走现有草稿、编辑、确认创建、任务看板、运行和智能决策流程。日程写入由 Hermes 使用飞书日历业务工具执行；如果工具要求高风险确认，必须走现有用户确认协议。

### 4. 数据流

普通自然语言读取：

1. 前端发送原始用户消息。
2. 后端附加通用工具选择契约，不做业务关键词路由。
3. Hermes 判断意图并调用业务 Tool。
4. Tool 返回真实数据或结构化错误。
5. Hermes 基于工具结果回答，并保留同会话上下文。

结构化写操作：

1. 用户点击快捷入口并补全模板。
2. 前端发送模板和受限 intent hint。
3. Hermes 校验字段并生成草稿或工具调用。
4. 平台展示可编辑草稿或高风险确认。
5. 用户确认后执行，取消则不产生写入。

## 错误处理

- MCP Resource 为空：继续判断并尝试业务 Tool，不向用户宣称业务数据为空。
- 飞书群名无匹配：报告当前授权身份下未找到匹配群，提示用户核对名称或可见范围。
- 飞书权限不足：返回缺失 scope 或当前身份无权访问，不回退成“没有资料”。
- lark-cli 参数错误：先使用 `lark_cli_help` 或 `lark_cli_schema` 修正一次；仍失败则返回具体错误。
- 外部服务超时：明确说明超时并允许重试，不生成未经证据支持的总结。
- 结构化模板字段缺失：在对话中列出缺失字段，不提交写操作。
- 高风险写操作：没有用户明确确认时不得自动追加 `--yes` 或执行写入。

## 测试设计

### 单元与契约测试

- 主 Agent 的每轮 instructions 包含通用工具选择契约。
- Knowledge Hermes 不获得飞书业务工具或该工具路由契约。
- 契约明确禁止用空 Resource 结果推断业务数据不存在。
- 飞书业务工具描述包含群名搜索和群消息读取用途。
- 快捷入口只填充模板，不直接调用创建或写入接口。
- intent hint 只能取允许的业务类型，客户端不能传任意系统指令。
- 现有定时任务草稿确认流程保持兼容。

### 真实全链路验收

使用原始问题：

`企业AI系统开发总结一下此群聊的开发进度`

验收要求：

1. Hermes 不得仅调用 `list_resources` 后结束。
2. Hermes 必须调用飞书业务 Tool，按名称找到“企业AI系统开发”。
3. Hermes 必须读取该群至少一页消息。
4. 回答必须基于返回的群消息内容总结，不能出现“没有已挂载资源所以无法总结”。
5. 同一问题在新会话中可独立完成，不依赖旧会话记忆。

另增加行业新闻验收：静态 Resource 为空时，Hermes 仍调用 `industry_news_latest` 并返回真实条目。

## 完成标准

- 原始飞书群聊问题在平台 AI 中连续两次新会话验收均成功。
- 日志显示使用业务 Tool，而不是把空 `list_resources` 当终止条件。
- 创建定时任务和添加日程快捷入口可生成结构化、可编辑内容。
- 所有写入仍经过草稿或高风险确认。
- 后端、Hermes MCP 和前端相关测试通过。
- 全链路重启后七个服务保持健康。
